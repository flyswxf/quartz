## 概述
工具执行层负责把模型提出的“动作意图”转为真实、可验证、可控制的外部操作。它是 [[工具调用(Action)#完整执行生命周期|工具调用]] 在工程中的落地点。

在简单示例里，工具层通常只是一个 `dict[name, function]`。但在真实系统中，仅有函数映射远远不够，还需要参数校验、执行隔离、超时控制、权限边界和结果标准化。

## 工具执行层的职责

### 1. 注册工具
维护工具名称、描述、参数模式、风险级别、幂等性、是否允许自动执行等元数据。

### 2. 校验参数
模型输出的 JSON 不能直接信任，必须进行结构和语义校验。

### 3. 控制执行
高风险工具要设置审批，外部请求要设置超时，本地命令要设置隔离环境。

### 4. 标准化结果
无论底层工具返回什么格式，最终都要转换成 harness 可稳定消费的 observation。

## 工具设计原则

### 1. Schema First
先定义输入输出模式，再实现工具逻辑。这样更适合模型调用，也更利于测试。

### 2. Least Privilege
默认只暴露完成任务所需的最小权限，不要让模型直接拥有通用 shell 权限。

### 3. Deterministic Observation
Observation 最好是结构化 JSON，而不是混杂日志与解释文本的长字符串。

### 4. Idempotency Awareness
要明确区分“查询类工具”和“有副作用工具”。前者可以更积极重试，后者必须谨慎。

## 规范实现示例
下面给出一个基于 `pydantic v2` 的工具注册与执行层实现。重点是参数校验、超时控制和统一返回格式。

```python
from __future__ import annotations

import json
from concurrent.futures import ThreadPoolExecutor, TimeoutError as FuturesTimeoutError
from dataclasses import dataclass
from typing import Any, Callable

from pydantic import BaseModel, Field, ValidationError


class WeatherInput(BaseModel):
    location: str = Field(min_length=1, max_length=100)
    unit: str = Field(default="celsius", pattern="^(celsius|fahrenheit)$")


def get_weather(params: WeatherInput) -> dict[str, Any]:
    # 这里应替换为真实 HTTP 客户端，并设置 timeout/retry
    return {
        "location": params.location,
        "temperature": 23,
        "unit": params.unit,
        "condition": "Sunny",
    }


@dataclass(slots=True)
class ToolSpec:
    name: str
    description: str
    input_model: type[BaseModel]
    handler: Callable[[BaseModel], dict[str, Any]]
    timeout_seconds: float = 5.0
    requires_approval: bool = False
    risk_level: str = "low"


class ToolRegistry:
    def __init__(self) -> None:
        self._tools: dict[str, ToolSpec] = {}

    def register(self, spec: ToolSpec) -> None:
        if spec.name in self._tools:
            raise ValueError(f"duplicate tool name: {spec.name}")
        self._tools[spec.name] = spec

    def get_openai_tool_schemas(self) -> list[dict[str, Any]]:
        schemas: list[dict[str, Any]] = []
        for spec in self._tools.values():
            schema = spec.input_model.model_json_schema()
            schemas.append(
                {
                    "type": "function",
                    "function": {
                        "name": spec.name,
                        "description": spec.description,
                        "parameters": schema,
                    },
                }
            )
        return schemas

    def execute(self, tool_name: str, raw_arguments: str) -> str:
        if tool_name not in self._tools:
            return json.dumps({"ok": False, "error": f"unknown_tool: {tool_name}"})

        spec = self._tools[tool_name]
        try:
            arguments = json.loads(raw_arguments)
        except json.JSONDecodeError as exc:
            return json.dumps({"ok": False, "error": f"invalid_json: {exc}"})

        try:
            validated = spec.input_model.model_validate(arguments)
        except ValidationError as exc:
            return json.dumps({"ok": False, "error": "validation_error", "detail": exc.errors()})

        with ThreadPoolExecutor(max_workers=1) as executor:
            future = executor.submit(spec.handler, validated)
            try:
                result = future.result(timeout=spec.timeout_seconds)
            except FuturesTimeoutError:
                return json.dumps({"ok": False, "error": "tool_timeout"})
            except Exception as exc:
                return json.dumps({"ok": False, "error": f"tool_execution_failed: {exc}"})

        return json.dumps({"ok": True, "result": result}, ensure_ascii=False)


registry = ToolRegistry()
registry.register(
    ToolSpec(
        name="get_weather",
        description="获取指定城市的当前天气。",
        input_model=WeatherInput,
        handler=get_weather,
        timeout_seconds=3.0,
        requires_approval=False,
        risk_level="low",
    )
)
```

## 为什么这种写法更规范

### 1. 参数模型独立
`WeatherInput` 让输入约束从业务逻辑中分离出来，模型输出不合法时会在进入工具前被拦截。

### 2. ToolSpec 明确表达元数据
超时、审批、风险等级不应散落在不同函数里，而应作为工具的一部分被统一管理。

### 3. 统一 observation 格式
所有工具都返回 `{"ok": ..., "result": ...}` 或 `{"ok": False, "error": ...}`，便于模型理解，也便于评测。

## 对高风险工具的额外要求
- 文件写入类工具要限制允许访问的目录。
- 数据库写操作要支持 dry-run 或审批模式。
- 网络请求要有 allowlist，禁止任意出站访问。
- 代码执行工具要运行在容器或沙箱中，不能直接执行宿主机命令。

如果工具本身是代码执行器，可以继续参考 [[Harness Engineering/子专题/03_Agent Sandbox 与 Code Interpreter#安全设计原则|Agent Sandbox 与 Code Interpreter]]。
