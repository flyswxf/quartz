## 概述
Harness 如果只有“能跑起来”的能力，而没有可靠性与安全性，那么它更像一个不受控的自动化脚本，而不是可上线的 Agent 系统。

可靠性关注系统在异常、噪声和外部依赖不稳定时是否仍能给出合理结果；安全性关注系统是否会越权、泄密、误执行危险动作，或者被提示注入操纵。

## 可靠性的目标

### 1. 限制故障传播
单次模型输出异常、单个工具失败，不应直接让整个会话不可恢复。

### 2. 避免无界执行
必须限制步数、时间、工具调用次数、输出大小和重试次数。

### 3. 支持降级
当工具不可用、记忆检索失败或模型返回非法结构时，系统应能进入简化路径而不是彻底崩溃。

## 安全性的目标

### 1. 权限最小化
模型不应直接拥有“任意命令执行”或“任意文件写入”的权限。

### 2. 明确可信边界
`system prompt`、用户输入、检索文档、工具 observation 的可信级别不同，不能混用。

### 3. 防止提示注入
外部网页、文档、API 返回值可能包含“忽略之前所有要求”之类的恶意文本，必须把它们当作不可信数据处理。

更细的攻击模式和工程防线可继续看 [[Harness Engineering/子专题/02_Prompt Injection Defense#防御层次|Prompt Injection Defense]]。

### 4. 防止秘密泄露
API Key、数据库密码、内部路径、用户隐私不应出现在模型可见上下文和最终输出中。

## 运行预算与熔断
最常见的可靠性控制手段包括：
- `max_steps`
- `max_tool_calls`
- `max_elapsed_seconds`
- `max_retries_per_tool`
- `max_consecutive_failures`

当某个阈值被触发时，系统应进入熔断状态，停止继续调用模型或工具。

## 高风险动作的防护

### 1. 审批门控
对删除文件、发送邮件、转账、写数据库等副作用操作，应要求人工审批。

更完整的审批状态机与人工接管模式可参考 [[Harness Engineering/子专题/04_Human-in-the-Loop 与 Approval Workflow#Approval Workflow 的最小状态机|Human-in-the-Loop 与 Approval Workflow]]。

### 2. Allowlist
只允许访问明确声明过的目录、URL 域名、数据库表或 API。

### 3. 参数净化
对文件路径、shell 参数、SQL 条件、URL query 参数做白名单和格式校验。

### 4. Observation 脱敏
工具返回值进入模型前，应先移除 token、cookie、手机号、邮箱等敏感字段。

## 规范实现示例
下面给出一个策略层示例，负责预算检查、审批和 observation 脱敏。

```python
from __future__ import annotations

import re
from dataclasses import dataclass


@dataclass(slots=True)
class ExecutionPolicy:
    max_steps: int = 8
    max_tool_calls: int = 8
    max_consecutive_failures: int = 3
    allow_write_tools: bool = False
    allowed_domains: tuple[str, ...] = ("api.weather.example", "api.search.example")


class PolicyGuard:
    EMAIL_RE = re.compile(r"[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}")
    TOKEN_RE = re.compile(r"(sk-[A-Za-z0-9]{20,}|AIza[0-9A-Za-z\-_]{20,})")

    def __init__(self, policy: ExecutionPolicy) -> None:
        self.policy = policy

    def check_budget(self, step_index: int, tool_calls: int, consecutive_failures: int) -> None:
        if step_index > self.policy.max_steps:
            raise RuntimeError("max_steps_exceeded")
        if tool_calls > self.policy.max_tool_calls:
            raise RuntimeError("max_tool_calls_exceeded")
        if consecutive_failures > self.policy.max_consecutive_failures:
            raise RuntimeError("max_consecutive_failures_exceeded")

    def require_approval(self, tool_name: str) -> bool:
        write_like_tools = {"write_file", "delete_file", "update_database", "send_email"}
        return tool_name in write_like_tools and not self.policy.allow_write_tools

    def validate_url(self, url: str) -> None:
        if not any(domain in url for domain in self.policy.allowed_domains):
            raise PermissionError("domain_not_allowed")

    def redact_observation(self, text: str) -> str:
        text = self.EMAIL_RE.sub("[REDACTED_EMAIL]", text)
        text = self.TOKEN_RE.sub("[REDACTED_TOKEN]", text)
        return text
```

## 设计点评

### 1. 策略独立于业务逻辑
`PolicyGuard` 不负责调用工具，它只负责定义“能不能调”和“结果能不能继续传播”。

### 2. 拒绝策略先于执行
高风险动作应该在真正执行之前就被拒绝或转入审批，而不是执行完再补救。

### 3. 脱敏先于注入
Observation 在进入主上下文前先做脱敏，这比在最终答案阶段再处理更安全。

## 常见攻击面
- **Prompt Injection**：外部文档命令模型忽略系统策略。
- **Tool Injection**：工具返回伪造指令，诱导后续模型调用高风险工具。
- **Data Exfiltration**：模型把内部信息拼接进最终回答。
- **Infinite Retry**：由于错误处理不当，系统在异常路径中无穷重试。

## 实践建议
- 对写操作类工具启用 `dry-run`。
- 对外部 observation 增加“不可执行、仅供参考”的显式标记。
- 对模型输出进行结构校验，不要直接相信自然语言里的“我已经完成了”。
- 对每次运行记录风险标签，便于事后追踪。
