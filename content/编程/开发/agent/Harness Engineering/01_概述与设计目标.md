## 概述
Harness Engineering 指的是围绕大语言模型构建一层稳定、可控、可观测、可扩展的执行框架，使 Agent 不只是“会回答”，而是能够持续、可靠地完成任务。

如果说 [[Agent概述#核心架构|Agent]] 描述的是能力组成，那么 Harness Engineering 描述的是这些能力在工程系统中的组织方式。它负责把 [[规划(Planning)#任务分解 (Task Decomposition)|规划]]、[[记忆(Memory)#记忆类型与生命周期|记忆]]、[[工具调用(Action)#完整执行生命周期|工具调用]]、[[多智能体系统(Multi-Agent)#典型协作模式|多智能体]] 这些能力编排成一个真正可运行的系统。

## 核心定义
在工程视角下，可以将 Agent 系统近似写成：
$$Agent\ System = Model + Context + State + Tools + Policies + Observability$$

其中：
- `Model`：负责理解、推理、生成。
- `Context`：负责把系统提示、历史消息、记忆、工具规格组织成输入。
- `State`：负责维护当前步骤、预算、任务中间结果、错误状态。
- `Tools`：负责与外部环境交互。
- `Policies`：负责安全边界、重试策略、退出条件、审批规则。
- `Observability`：负责日志、指标、链路追踪、回放与评测。

上述六部分合在一起，构成了 Agent 的 harness。

## 为什么它重要
很多 Agent 原型在 Demo 阶段看起来可用，但进入真实环境后会暴露出系统性问题：

### 1. 不稳定
同一个问题反复执行，可能产生不同的工具调用序列，甚至死循环。

### 2. 不可控
模型可能越权调用工具、误删数据、无限重试，或者在注入攻击下偏离目标。

### 3. 不可观测
当回答错误时，难以判断问题出在提示构造、工具返回、记忆召回还是模型推理。

### 4. 不可扩展
随着工具增多、上下文变长、任务变复杂，简单的单轮函数调用代码很快会失控。

Harness Engineering 的目标就是解决这些问题。

## 设计目标

### 1. 可预测性
系统需要有清晰的状态迁移、步数上限、超时预算与退出条件。

### 2. 可维护性
模型调用、工具执行、上下文构造、记忆管理、日志采集要分层实现，避免所有逻辑耦合在一个函数中。

### 3. 安全性
工具权限要最小化，输入要校验，输出要脱敏，外部副作用要可追踪。

### 4. 可观测性
每一步 Thought、Action、Observation 都应留下结构化记录，便于回放与评测。

### 5. 可演化性
从单 Agent 扩展到 [[多智能体系统(Multi-Agent)#典型协作模式|多智能体]] 时，不应该推翻现有执行框架，而应在原有 harness 上继续扩展。

## 分层结构

### 1. 控制层
负责接受用户请求、创建运行会话、设定预算和策略、驱动主循环。

### 2. 上下文层
负责拼接系统提示、历史消息、检索记忆、工具规格、输出约束。详见 [[Harness Engineering/03_上下文工程(Context Engineering)#上下文装配的目标|上下文工程]]。

### 3. 执行层
负责调度模型调用和工具调用，将自然语言决策转为真实动作。详见 [[Harness Engineering/02_运行时循环与状态机#运行时循环的最小闭环|运行时循环]] 与 [[Harness Engineering/04_工具注册与执行层#工具执行层的职责|工具执行层]]。

### 4. 策略层
负责超时、重试、审批、降级、风险拦截。详见 [[Harness Engineering/05_可靠性与安全#可靠性的目标|可靠性与安全]]。

### 5. 观测层
负责日志、指标、trace、评测与回放。详见 [[Harness Engineering/06_评测与可观测性#可观测性的目标|评测与可观测性]]。

## 常见失效模式
- **上下文污染**：历史消息和工具结果未经筛选直接拼接，导致模型注意力分散。
- **工具雪崩**：一次错误决策触发多个昂贵或危险工具调用。
- **记忆误召回**：召回结果语义相近但事实错误，导致后续回答被污染。
- **无限循环**：模型在 `thought -> action -> observation` 中无法收敛。
- **错误放大**：一个失败的工具结果被模型反复引用，逐步演变成完整但错误的答案。
