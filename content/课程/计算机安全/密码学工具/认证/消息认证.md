# 消息认证 (Message Authentication)

## 基本概念

### 定义
消息认证是一种确保**收到的消息确实是声称的发送方所发出、且内容未被篡改**的密码学机制。它回答两个关键问题：
1. **消息来源是否可信？** —— 发送方认证 (Source / Data Origin Authentication)
2. **消息是否被修改过？** —— 完整性保护 (Integrity Protection)

### 与机密性的区别

消息认证和消息加密是**两个独立的安全目标**：

| 安全目标                      | 解决的问题                     | 典型实现                                           |
| ----------------------------- | ------------------------------ | -------------------------------------------------- |
| **机密性 (Confidentiality)**  | 外人能否读取消息内容？         | [[对称加密\|对称加密]]、[[非对称加密\|非对称加密]] |
| **消息认证 (Authentication)** | 消息是否来自可信方且未被篡改？ | [[消息认证码(MAC)\|MAC]]、[[数字签名\|数字签名]]   |

> 加密**不自动提供**认证，认证**不自动提供**加密。两者需要分别实现。

## 消息认证的两大实现路径

### 路径对比

| 维度           |    消息认证码 (MAC)    |             数字签名 (DS)             |
| -------------- | :--------------------: | :-----------------------------------: |
| **密码体制**   |       对称密码学       |              公钥密码学               |
| **密钥类型**   |  共享密钥 (双方持有)   | 私钥 (仅发送方) + 公钥 (任何人可验证) |
| **验证方**     | 仅持有共享密钥的接收方 |           任何拥有公钥的人            |
| **不可抵赖性** |        ❌ 不提供        |                ✅ 提供                 |
| **第三方裁决** |        ❌ 不可能        |                ✅ 可能                 |
| **计算开销**   |           低           |                  高                   |
| **典型应用**   |   TLS 记录层、IPsec    |       软件签名、证书、数字信封        |

### MAC：对称路径
使用收发双方共享的密钥生成认证标签。详见 [[消息认证码(MAC)|消息认证码笔记]]。

### 数字签名：非对称路径
使用发送方私钥生成签名，任何人用公钥验证。详见 [[数字签名|数字签名笔记]]。

## 消息认证提供的安全服务详解

### 1. 消息完整性 (Message Integrity)
确保消息在传输过程中未被任何方式（意外或恶意）修改。

**实现原理：** 认证标签/签名是消息内容的密码学函数。任何对消息的修改都会导致验证失败。

**场景（习题 2.5a）：** Oscar 拦截 Alice 发给 Bob 的 "Transfer \$1000 to Mark" 并将 "Mark" 改为 "Oscar"。Bob 计算收到的消息的认证值，发现与附带的认证值不匹配 → 检测到篡改。

### 2. 消息来源认证 (Data Origin Authentication)
确保消息确实来自声称的发送方。

**实现原理：**
- MAC：只有知晓共享密钥的双方能生成有效标签
- DS：只有私钥持有者能生成有效签名

**场景（习题 2.5c）：** Oscar 声称自己向 Bob 发送了某消息，但 Alice 也声称是她发送的。如果附带的认证值是能用 Alice 公钥验证的签名，则一定来自 Alice (Oscar 没有 Alice 的私钥) → Bob 能分辨。

### 3. 不可抵赖性 (Non-Repudiation) —— 仅数字签名提供

|                  |                         MAC                          |                   DS                    |
| ---------------- | :--------------------------------------------------: | :-------------------------------------: |
| 提供不可抵赖性？ |                          ❌                           |                    ✅                    |
| 原因             | Bob 和 Alice 持有同一密钥，Bob 可自行生成任何 MAC 值 | 只有 Alice 有私钥，Bob 无法伪造有效签名 |

**场景（习题 2.5d）：** Bob 声称从 Alice 收到了消息并拿出了验证通过的认证值，但 Alice 否认发送。
- MAC：第三方无法裁决，因为 Bob 也能生成同样的 MAC
- DS：第三方可以裁决——如果签名能用 Alice 公钥验证，则 Alice 确实签过；如果 Bob 无法提供有效签名，则 Alice 清白

## 重放攻击与消息认证的局限

**任何纯消息认证机制都无法单独防御重放攻击**（习题 2.5b）。

Oscar 截获 Alice 的合法消息和认证值，重新发送给 Bob 100 次。每次验证都会通过，因为消息内容完全相同，认证值也仍然有效。

**防御重放攻击的辅助机制：**

| 机制                                    | 原理                                         |
| --------------------------------------- | -------------------------------------------- |
| **序列号 (Sequence Number)**            | 每条消息附带递增编号，接收方拒绝已见过的序号 |
| **时间戳 (Timestamp)**                  | 消息包含发送时间，接收方拒绝过期消息         |
| **随机数 (Nonce / Challenge-Response)** | 接收方先发送随机数，发送方将其纳入认证计算   |

这些机制需要与消息认证结合使用，见 [[消息认证码(MAC)#场景 b：重放攻击|MAC 中的重放防御]]。

## 机密性与认证的复合：认证加密 (Authenticated Encryption)

在实际通信系统中，**机密性和消息认证通常需要同时满足**。现代密码学提倡使用认证加密模式，将两者合并为一个安全操作。

### 三种组合策略及其安全性

| 策略                 | 描述                         | 安全性                           |
| -------------------- | ---------------------------- | -------------------------------- |
| **Encrypt-then-MAC** | 先加密，再对密文计算 MAC     | ✅ 推荐，最安全                   |
| **Encrypt-and-MAC**  | 分别对明文加密和计算 MAC     | ⚠️ MAC 可能泄露明文信息           |
| **MAC-then-Encrypt** | 先对明文计算 MAC，再一起加密 | ⚠️ 存在 padding oracle 等攻击风险 |

### 专用认证加密算法

现代方案直接提供认证加密，无需手动组合：

| 算法                  | 全称                | 结构                                  |
| --------------------- | ------------------- | ------------------------------------- |
| **AES-GCM**           | Galois/Counter Mode | CTR 加密 + GHASH 认证                 |
| **AES-CCM**           | CBC-MAC + CTR       | CBC-MAC 认证 + CTR 加密               |
| **ChaCha20-Poly1305** | ChaCha20 + Poly1305 | ChaCha20 流加密 + Poly1305 一次性认证 |

TLS 1.3 仅允许使用经过认证的加密套件（如 AES-GCM、ChaCha20-Poly1305），反映了消息认证在现代通信中的核心地位。
