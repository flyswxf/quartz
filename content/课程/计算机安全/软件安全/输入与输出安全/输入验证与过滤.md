## 核心原则：绝不信任用户输入 (Never Trust User Input)

软件安全的一条黄金法则是：**任何跨越系统信任边界进入系统的数据都应被视为不可信的。** 无论是来自表单提交、URL 参数、HTTP 头部，还是读取自文件、环境变量、甚至数据库中的旧数据，都必须经过严格的验证。

输入处理不当是导致注入攻击（[[SQL注入攻击|SQLi]]、[[跨站脚本攻击(XSS)]]、命令注入）和内存溢出等漏洞的根本原因。

## 输入验证的策略

输入验证主要分为两种策略：**白名单 (Allowlist)** 和 **黑名单 (Denylist)**。

### 1. 白名单策略（推荐）
白名单验证是指明确定义“什么是合法的输入”，拒绝所有不符合定义的输入。
- **优点：** 安全性高。随着攻击手段的不断演进，未知的恶意输入层出不穷，白名单能够有效防御这些未知攻击。
- **缺点：** 实现相对复杂，需要精确理解业务逻辑对数据的要求。
- **示例：** 如果要求用户输入年龄，白名单规则应该是：输入必须只包含数字，且范围在 0 到 120 之间。

### 2. 黑名单策略（不推荐）
黑名单验证是指明确定义“什么是恶意的输入”（如禁止输入 `'`、`<script>` 等），如果输入匹配黑名单则被拒绝。
- **优点：** 实现简单，容易快速修补已知漏洞。
- **缺点：** 极易被绕过。攻击者可以使用不同的编码（如 URL 编码、HTML 实体编码）、大小写变形（如 `<sCrIpT>`）或寻找黑名单中未包含的恶意载荷。

## 验证的维度

一个完善的输入验证应该涵盖以下几个维度：
1. **存在性与非空：** 确保必需的数据已提供。
2. **数据类型：** 验证输入是否为预期的类型（如整数、布尔值、字符串）。
3. **长度限制：** 检查字符串或字节数组的最大和最小长度，防止缓冲区溢出和资源耗尽。
4. **范围检查：** 对于数值或日期，验证其是否在合理的区间内。
5. **格式验证：** 使用正则表达式或专门的解析库验证输入格式（如邮箱地址、IP 地址、UUID）。

## 过滤与清理 (Sanitization)

当无法直接拒绝不合法输入，或者需要对输入进行宽容处理时，可以使用清理/过滤技术。
- **清理：** 从输入中移除或修改潜在的危险字符。
- **注意：** 清理操作必须非常谨慎。简单的字符替换（如将 `<script>` 替换为空）可能导致漏洞。例如，如果输入是 `<scr<script>ipt>`，替换后就变成了 `<script>`，从而绕过了防护。
- **最佳实践：** 过滤和清理通常作为输入验证的辅助手段，不应取代严格的白名单验证。

## 在何处进行验证？

- **客户端验证：** 用于提升用户体验，提供即时反馈。**但绝不能作为安全防线**，因为攻击者可以轻易绕过客户端代码（如使用代理工具直接发送 HTTP 请求）。
- **服务端验证：** 真正的安全防线。所有到达服务端的数据必须重新进行完整的验证。
- **纵深防御：** 在应用层的不同组件（如 API 网关、Controller 层、ORM 层）进行多重验证。
