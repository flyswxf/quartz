## 输入验证不足以保证安全

虽然输入验证（特别是[[输入验证与过滤#1. 白名单策略（推荐）|白名单验证]]）是安全防御的第一道防线，但它不能解决所有问题。有时候，应用程序必须接受包含特殊字符的输入（例如，用户名字中包含撇号 `O'Brian`，或者用户在技术论坛讨论 `<script>` 标签）。

如果仅仅依赖输入验证，我们可能会拒绝这些合法输入。因此，**输出编码 (Output Encoding) 和转义 (Escaping)** 是防御注入类攻击（特别是 XSS）的关键防线。

## 核心原则：数据不应被误认为控制字符

输出编码的核心目的是确保当数据被发送到解释器（如浏览器、数据库、终端）时，解释器会**将这些数据严格视为内容，而不是可执行的代码或控制指令**。

## 针对不同上下文的编码策略

数据最终呈现在哪里（上下文），决定了应该使用何种编码方式。

### 1. HTML 上下文编码
当数据作为 HTML 标签的内容呈现时（例如 `<div>${user_data}</div>`）：
- 必须将 HTML 的保留字符转换为 HTML 实体。
- `&` 转换为 `&amp;`
- `<` 转换为 `&lt;`
- `>` 转换为 `&gt;`
- `"` 转换为 `&quot;`
- `'` 转换为 `&#x27;`

### 2. HTML 属性上下文编码
当数据作为 HTML 标签的属性值呈现时（例如 `<input value="${user_data}">`）：
- 仅仅编码 `<` 和 `>` 是不够的，因为攻击者可以通过闭合引号来跳出属性并添加新属性（如 `onload`）。
- 最佳实践是：除了字母和数字，将所有字符编码为 HTML 实体或使用特定属性的转义规则。

### 3. JavaScript 上下文编码
当数据被动态插入到 JavaScript 代码块中时（例如 `<script>var name = '${user_data}';</script>`）：
- 不能使用 HTML 实体编码，因为 JS 解析器不理解它。
- 必须使用 JavaScript 编码，通常是将字符转换为 Unicode 格式（如将 `'` 转换为 `\u0027`）。
- 避免直接在 JS 中拼接数据，更安全的做法是将数据放在 HTML 的 `data-*` 属性中，然后在 JS 中读取，或者通过 JSON API 获取数据。

### 4. URL 上下文编码
当数据作为 URL 参数拼接时（例如 `<a href="/search?q=${user_data}">`）：
- 必须进行 URL 编码（Percent-encoding）。
- 将空格转换为 `%20` 或 `+`，特殊字符转换为其十六进制表示（如 `%` 变为 `%25`）。

## 安全实践建议

1. **使用成熟的编码库：** 不要自己编写编码函数，容易遗漏边缘情况。使用成熟的库，如 OWASP Java Encoder、DOMPurify 等。
2. **上下文感知：** 编码函数必须与数据即将插入的上下文匹配。
3. **不要双重编码：** 确保数据只被编码一次，否则会导致显示错误。通常，数据在数据库中应以原始格式存储，**只在输出渲染的那一刻进行编码**。
4. **利用现代框架的内置保护：** React、Vue.js 等前端框架默认会对插值表达式（如 `{{ message }}`）进行 HTML 编码。但仍需注意危险 API 的使用（如 React 的 `dangerouslySetInnerHTML` 或 Vue 的 `v-html`）。
