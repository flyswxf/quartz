# 错误处理与日志记录

正确的错误处理和日志记录机制不仅对于软件调试和运维至关重要，也是安全防护体系中不可或缺的一环。

## 1. 错误处理与信息泄露

当应用程序遇到异常情况（如数据库连接失败、无效输入、文件找不到）时，如何向用户展示错误信息是一个关键的安全决策。

### 核心原则：安全失败 (Fail Securely)
如果系统由于错误或异常而无法继续正常处理，它必须回退到一个安全的状态，拒绝访问，而不是授予默认访问权限或崩溃导致状态未知。

### 防止信息泄露
- **向用户展示通用信息：** 应用程序展示给终端用户的错误信息应尽可能模糊和通用（例如：“系统内部错误，请稍后再试”）。
- **绝不暴露内部细节：** 绝不能在生产环境的响应中包含堆栈跟踪 (Stack Traces)、数据库查询语句、服务器内部 IP 地址或框架版本信息。这些信息对于攻击者来说是极具价值的侦察数据，可以帮助他们精确定位系统漏洞。
- **全局异常处理：** 在应用框架层面配置全局异常捕获机制，确保任何未被捕获的异常都能被统一处理，转换为友好的通用提示，防止底层错误直接抛出到前端。

## 2. 安全日志记录 (Secure Logging)

日志是发现攻击行为、进行安全审计和事后取证（事件响应）的唯一依据。

### 记录什么？
应记录所有与安全相关的关键事件，包括但不限于：
- 成功的认证和失败的认证尝试。
- 权限变更和密码修改。
- 对敏感数据（如个人隐私数据、财务数据）的访问。
- 授权失败（越权访问尝试）。
- 输入验证失败（可能是攻击尝试的早期信号）。
- 系统启动、关闭或关键配置的更改。

### 日志应包含的信息
为了使日志具有审计价值，每条安全日志通常应回答以下问题（"谁、什么、何时、何地"）：
- 时间戳（需同步到标准时间服务器 NTP）。
- 用户标识（User ID 或 Session ID，如果已认证）。
- 事件类型或操作描述。
- 来源 IP 地址。

### 日志记录的安全风险
日志系统本身也可能成为攻击目标或数据泄露的源头：
- **敏感数据脱敏：** **绝不能**在日志中记录用户的明文密码、完整的信用卡号、有效的会话令牌 (Session Token) 等极端敏感信息。在写入日志前必须对这些数据进行掩码或散列处理。
- **日志注入攻击 (Log Injection)：** 如果用户输入未经清理直接写入日志，攻击者可以注入换行符来伪造日志条目，或者注入终端控制字符/恶意脚本，当管理员查看日志时触发漏洞（如 XSS）。必须对写入日志的数据进行适当的编码。
- **日志保护：** 日志文件应当受到严格的访问控制，仅允许授权的运维和安全人员访问。为了防止攻击者在入侵后篡改或删除日志以掩盖踪迹，应将日志实时发送到独立的、安全的集中式日志服务器（如 ELK 堆栈或 SIEM 系统），并配置为追加写入（Append-only）。
