在软件开发中，正确应用密码学技术是保护数据机密性和完整性的关键。然而，密码学极易被误用，导致虚假的安全感。

## 黄金法则：永远不要自己发明加密算法

密码学是一门高度专业化的数学学科。任何由非专业人员设计、未经全球学术界长期审查的自创算法，几乎必定存在致命缺陷。
- **最佳实践：** 必须使用标准的、广受审查的公开算法（如 AES, RSA, SHA-256）和成熟的加密库（如 OpenSSL, Bouncy Castle, libsodium）。

## 1. 保护存储中的数据 (Data at Rest)

### 密码存储 (Password Storage)
用户的密码绝对不能以明文存储，也不能使用可逆的加密算法存储。
- **错误做法：** 明文存储、使用 MD5 或 SHA-1 等快速哈希算法（容易被彩虹表或暴力破解）。
- **正确做法：** 使用加盐的慢速哈希算法。
  - **盐 (Salt)：** 为每个用户生成一个唯一的随机字符串，与密码拼接后再进行哈希。这可以挫败彩虹表攻击，并确保相同密码的用户拥有不同的哈希值。
  - **慢速哈希算法：** 使用如 **Argon2**, **Bcrypt**, **Scrypt** 或 PBKDF2。这些算法被设计为计算密集型或内存密集型，显著增加了攻击者暴力破解的成本。

### 敏感数据加密
对于需要还原的敏感数据（如信用卡号、个人身份信息），应使用对称或非对称加密。
- 推荐使用经过认证的加密模式 (Authenticated Encryption)，如 **AES-GCM** 或 **ChaCha20-Poly1305**。它们不仅提供机密性，还提供数据完整性校验，防止密文被恶意篡改。

## 2. 保护传输中的数据 (Data in Transit)

数据在网络上传输时，极易遭到窃听（嗅探）或中间人攻击 (Man-in-the-Middle, MitM)。
- **强制使用 HTTPS/TLS：** 所有包含敏感数据的通信（甚至是内网服务间的通信）都应使用 TLS 协议加密。
- **废弃不安全的协议：** 禁用 SSL v2/v3 以及 TLS 1.0/1.1，仅支持 **TLS 1.2 及以上版本**（推荐 TLS 1.3）。
- **证书验证：** 客户端代码（如移动应用或后端服务调用 API 时）必须严格验证服务器的 SSL/TLS 证书是否有效、未过期且由受信任的 CA 签发。绝不能在生产代码中忽略证书校验错误。

## 3. 密钥管理

加密系统的安全性往往不取决于算法本身，而是取决于密钥的安全性（Kerckhoffs 原则）。如果密钥泄露，加密形同虚设。
- **绝不硬编码：** 永远不要将 API 密钥、数据库密码或加密密钥硬编码在源代码中，防止它们随代码被提交到版本控制系统（如 GitHub）。
- **使用环境变量或密钥管理系统：** 密钥应通过环境变量注入，或者使用专门的密钥管理服务（KMS，如 AWS KMS, HashiCorp Vault, HashiCorp Vault）进行存储、轮换和访问控制。
- **定期轮换：** 密钥应具有生命周期，并定期更换，以限制一旦密钥泄露造成的损失。

## 4. 随机数生成

密码学操作（如生成密钥、初始化向量 IV、盐值、会话 Token）需要高质量的随机数。
- **错误做法：** 使用语言标准库中的普通伪随机数生成器（如 C 语言的 `rand()`, Java 的 `java.util.Random`）。这些函数生成的序列是可预测的。
- **正确做法：** 必须使用**[[随机与伪随机数#3. 密码学安全伪随机数生成器 (CSPRNG)|密码学安全的伪随机数生成器 (CSPRNG)]]**。例如 Java 中的 `java.security.SecureRandom`，Linux 系统下的 `/dev/urandom`。
