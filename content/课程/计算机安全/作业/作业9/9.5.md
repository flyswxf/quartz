# 9.5 SMTP 包过滤规则集分析

## 题目

SMTP（简单邮件传输协议）是基于 TCP 在主机之间传输邮件的标准协议。用户代理与服务器程序之间建立 TCP 连接，服务器在 TCP 端口 25 上监听传入的连接请求，连接的用户端使用 1023 以上的 TCP 端口号。

假设希望构建一个包过滤规则集来允许入站和出站的 SMTP 流量，并生成了如下规则集：

| Rule | Direction | Src Addr | Dest Addr | Protocol | Dest Port | Action |
| :--- | :-------- | :------- | :-------- | :------- | :-------- | :----- |
| A    | In        | External | Internal  | TCP      | 25        | Permit |
| B    | Out       | Internal | External  | TCP      | >1023     | Permit |
| C    | Out       | Internal | External  | TCP      | 25        | Permit |
| D    | In        | External | Internal  | TCP      | >1023     | Permit |
| E    | Either    | Any      | Any       | Any      | Any       | Deny   |

**a.** 描述每条规则的效果。

**b.** 主机 IP 地址为 `172.16.1.1`，远程主机 `192.168.3.4` 尝试发送邮件，同时本地用户也尝试向远程 SMTP 服务器发送邮件。判断四个数据包是被允许还是拒绝，并指出使用的规则。

**c.** 外部主机 `10.1.2.3` 从端口 `5150` 尝试连接本地主机 `172.16.3.4` 上端口 `8080` 的 Web 代理服务器以实施攻击。判断攻击是否成功。

---

## 讲解

### SMTP 通信模型

SMTP 通信涉及两种典型场景：

1. **接收邮件**：外部主机（客户端，端口 >1023）→ 本地 SMTP 服务器（端口 25）
2. **发送邮件**：本地主机（客户端，端口 >1023）→ 外部 SMTP 服务器（端口 25）

TCP 是面向连接的协议，通信双方都需要发送和接收数据，因此规则集需要同时覆盖双向流量。

### 包过滤的匹配机制

包过滤防火墙（Packet Filter）按**从上到下**的顺序匹配规则，**首个匹配的规则生效**，后续规则不再检查。最后一行 Rule E 作为默认拒绝策略（Default Deny），未被前面规则匹配的流量都会被丢弃。

---

## 题目分析

### a. 各规则的效果

逐条分析每条规则的意图和作用：

**Rule A** — 允许**外部主机**向**本地主机端口 25** 发起 TCP 连接。这使得外部用户可以向本地 SMTP 服务器发送邮件。对应场景：远程客户端 → 本地 SMTP 服务器。

**Rule B** — 允许**本地主机**向**外部主机端口 >1023** 发送 TCP 流量。这使得本地 SMTP 服务器能够回复外部客户端（客户端使用高位端口）。这是 Rule A 的配套规则，用于 SMTP 会话中服务器对客户端的响应。

**Rule C** — 允许**本地主机**向**外部主机端口 25** 发起 TCP 连接。这使得本地用户可以向外部 SMTP 服务器发送邮件。对应场景：本地客户端 → 远程 SMTP 服务器。

**Rule D** — 允许**外部主机**向**本地主机端口 >1023** 发送 TCP 流量。这使得外部 SMTP 服务器能够回复本地客户端（本地客户端使用高位端口）。这是 Rule C 的配套规则。

**Rule E** — 默认拒绝所有未被上述规则匹配的流量。这是**隐式拒绝**（Implicit Deny）策略，确保安全性。

> 整体规则集的设计逻辑：A+B 配合实现**入站 SMTP**（接收邮件），C+D 配合实现**出站 SMTP**（发送邮件），E 作为兜底拒绝一切其他流量。

---

### b. 四个数据包的判定

| Packet | Direction | Src Addr    | Dest Addr   | Protocol | Dest Port | 匹配规则   | Action     |
| :----- | :-------- | :---------- | :---------- | :------- | :-------- | :--------- | :--------- |
| 1      | In        | 192.168.3.4 | 172.16.1.1  | TCP      | 25        | **Rule A** | **Permit** |
| 2      | Out       | 172.16.1.1  | 192.168.3.4 | TCP      | 1234      | **Rule B** | **Permit** |
| 3      | Out       | 172.16.1.1  | 192.168.3.4 | TCP      | 25        | **Rule C** | **Permit** |
| 4      | In        | 192.168.3.4 | 172.16.1.1  | TCP      | 1357      | **Rule D** | **Permit** |

具体分析：

- **Packet 1**：远程主机 `192.168.3.4` 向本地 SMTP 服务器（端口 25）发起连接，方向为入站，源地址为外部，目的端口为 25，精确匹配 **Rule A**，允许通过。
- **Packet 2**：本地 SMTP 服务器回复远程客户端，方向为出站，源地址为内部，目的端口为 1234（>1023），精确匹配 **Rule B**，允许通过。
- **Packet 3**：本地用户向远程 SMTP 服务器（端口 25）发起连接，方向为出站，源地址为内部，目的端口为 25，精确匹配 **Rule C**，允许通过。
- **Packet 4**：远程 SMTP 服务器回复本地客户端，方向为入站，源地址为外部，目的端口为 1357（>1023），精确匹配 **Rule D**，允许通过。

---

### c. 攻击是否成功

| Packet | Direction | Src Addr   | Dest Addr  | Protocol | Dest Port | 匹配规则   | Action     |
| :----- | :-------- | :--------- | :--------- | :------- | :-------- | :--------- | :--------- |
| 5      | In        | 10.1.2.3   | 172.16.3.4 | TCP      | 8080      | **Rule D** | **Permit** |
| 6      | Out       | 172.16.3.4 | 10.1.2.3   | TCP      | 5150      | **Rule B** | **Permit** |

- **Packet 5**：外部主机 `10.1.2.3` 试图从端口 5150 连接本地 `172.16.3.4` 的端口 8080（Web 代理服务器）。方向为入站，目的端口为 8080。逐条检查规则：Rule A 要求目的端口为 25，不匹配；Rule B、C 为出站方向，不匹配；而 Rule D 要求入站方向、外部→内部、TCP、目的端口 >1023，Packet 5 完全满足这些条件（$8080 > 1023$），因此被 **Rule D 允许**。外部攻击者的 SYN 包能够到达本地 Web 代理服务器。
- **Packet 6**：本地 Web 代理服务器的出站响应包，目的端口 5150 满足 Rule B 的 ">1023" 条件（$5150 > 1023$），被 **Rule B 允许**。本地服务器的响应包能够返回给攻击者。

TCP 三次握手可以正常完成，攻击者能够与 Web 代理服务器建立完整的 TCP 连接，因此**攻击能够成功**。

> **根本原因**：Rule D 设计为配合 Rule C 使用（允许外部 SMTP 服务器回复本地客户端），但由于其匹配条件过于宽泛——只要求入站方向、外部→内部、TCP、目的端口 >1023——它会**意外允许所有目的端口大于 1023 的入站连接**，包括非 SMTP 的服务（如本例中的 Web 代理端口 8080）。这体现了包过滤规则设计中"过度宽松"带来的安全隐患。

---

## 参考答案

**a.** Rule A 允许外部主机向本地 SMTP 服务器（端口 25）建立入站连接，实现接收邮件功能；Rule B 允许本地 SMTP 服务器向外部客户端的高位端口（>1023）发送出站响应，是 Rule A 的配套规则；Rule C 允许本地主机向外部 SMTP 服务器（端口 25）建立出站连接，实现发送邮件功能；Rule D 允许外部 SMTP 服务器向本地客户端的高位端口（>1023）发送入站响应，是 Rule C 的配套规则；Rule E 作为默认策略拒绝所有未匹配的流量，确保安全性。

**b.** Packet 1（远程主机发送邮件到本地）方向入站、目的端口 25，匹配 Rule A，允许通过；Packet 2（本地 SMTP 服务器回复远程客户端）方向出站、目的端口 1234（>1023），匹配 Rule B，允许通过；Packet 3（本地用户发送邮件到远程）方向出站、目的端口 25，匹配 Rule C，允许通过；Packet 4（远程 SMTP 服务器回复本地客户端）方向入站、目的端口 1357（>1023），匹配 Rule D，允许通过。四个数据包均被允许。

**c.** 攻击能够成功。Packet 5 为入站连接请求，虽然目的端口是 8080 而非 25，但 $8080 > 1023$，满足 Rule D 的条件（入站、外部→内部、TCP、目的端口 >1023），因此被 Rule D 允许通过；Packet 6 为本地 Web 代理服务器的出站响应，目的端口 5150 满足 Rule B 的 >1023 条件，同样被允许。两个方向的数据包均通过过滤，TCP 三次握手可以完成，攻击者能够与 Web 代理服务器建立连接并实施攻击。问题的根源在于 Rule D 的设计过于宽泛，其 ">1023" 的端口范围远超 SMTP 所需，导致本应用于 SMTP 回复的规则意外放行了非 SMTP 服务的入站连接。
