# 9.6 改进的 SMTP 包过滤规则集分析

## 题目

为了提供更多的保护，前一个问题（9.5）中的规则集被修改如下：

| Rule | Direction | Src Addr | Dest Addr | Protocol | Src Port | Dest Port | Action |
| :--- | :-------- | :------- | :-------- | :------- | :------- | :-------- | :----- |
| A    | In        | External | Internal  | TCP      | >1023    | 25        | Permit |
| B    | Out       | Internal | External  | TCP      | 25       | >1023     | Permit |
| C    | Out       | Internal | External  | TCP      | >1023    | 25        | Permit |
| D    | In        | External | Internal  | TCP      | 25       | >1023     | Permit |
| E    | Either    | Any      | Any       | Any      | Any      | Any       | Deny   |

**a.** 描述所做的更改。

**b.** 将这个新的规则集应用于前一个问题的六个相同的数据包。指出哪些数据包被允许或拒绝，并在每种情况下指出了使用了哪条规则。

---

## 讲解

### 规则的改进分析

在 9.5 题中，规则集只检查了**目的端口（Dest Port）**。这导致了旧 Rule D 存在漏洞：只要是外部向内部发起的 TCP 请求，且目的端口大于 1023，就会被放行。攻击者正是利用了这一点，向本地的 8080 端口（>1023）发起了攻击。

9.6 题中的新规则集增加了**源端口（Src Port）**的检查字段：
1. 对于客户端发起的请求（Rule A 和 Rule C），除了要求目的端口是 25（SMTP 服务），还明确要求源端口必须是大于 1023 的临时端口。
2. 对于服务器返回的响应（Rule B 和 Rule D），除了要求目的端口是大于 1023 的客户端临时端口，还**强制要求源端口必须是 25**。

这使得规则集与 SMTP 的真实通信特征实现了严格的双向绑定，避免了端口被其他服务滥用的情况。

---

## 题目分析

### b. 数据包应用分析

根据 9.5 题的场景，我们可以推断出这六个数据包的源端口和目的端口特征：

- **Packet 1**：远程客户端请求本地 SMTP 服务器。方向为入站，源端口为客户端高位端口（>1023），目的端口为 25。
- **Packet 2**：本地 SMTP 服务器回复远程客户端。方向为出站，源端口为 25，目的端口为 1234（>1023）。
- **Packet 3**：本地客户端请求远程 SMTP 服务器。方向为出站，源端口为本地高位端口（如 1357），目的端口为 25。
- **Packet 4**：远程 SMTP 服务器回复本地客户端。方向为入站，源端口为 25，目的端口为 1357（>1023）。
- **Packet 5**：外部攻击者请求本地 Web 代理。方向为入站，源端口为 5150（>1023），目的端口为 8080（>1023）。
- **Packet 6**：本地 Web 代理回复外部攻击者。方向为出站，源端口为 8080（>1023），目的端口为 5150（>1023）。

逐一匹配新规则集：

1. **Packet 1**：In 方向，Src Port >1023，Dest Port 25。匹配 **Rule A**，**Permit**。
2. **Packet 2**：Out 方向，Src Port 25，Dest Port 1234（>1023）。匹配 **Rule B**，**Permit**。
3. **Packet 3**：Out 方向，Src Port >1023（如1357），Dest Port 25。匹配 **Rule C**，**Permit**。
4. **Packet 4**：In 方向，Src Port 25，Dest Port 1357（>1023）。匹配 **Rule D**，**Permit**。
5. **Packet 5**：In 方向，Src Port 5150，Dest Port 8080。Dest Port 不是 25（不匹配 Rule A），Src Port 不是 25（不匹配 Rule D）。落入 **Rule E**，**Deny**。
6. **Packet 6**：Out 方向，Src Port 8080，Dest Port 5150。Src Port 不是 25（不匹配 Rule B），Dest Port 不是 25（不匹配 Rule C）。落入 **Rule E**，**Deny**。

---

## 参考答案

**a.** 更改在于规则集中增加了对“源端口（Src Port）”的严格检查。旧规则仅检查目的端口，导致本应用于允许 SMTP 服务器响应的规则（如旧 Rule D）错误地放行了其他非 SMTP 服务的入站连接（如 8080 端口的 Web 代理）。新规则通过双向绑定 SMTP 的端口特征（即服务器端口固定为 25，客户端端口大于 1023），例如明确要求入站的响应包（Rule D）必须来自外部的 25 端口，从而实现了更细粒度的访问控制，修补了旧规则中过于宽泛的漏洞。

**b.** 应用新规则集后，四个合法的 SMTP 数据包均被允许，而两个攻击数据包均被拒绝：
- **Packet 1**（远程主机发送邮件到本地）：满足入站、源端口>1023、目的端口 25，匹配 Rule A，被允许（Permit）。
- **Packet 2**（本地 SMTP 服务器回复远程）：满足出站、源端口 25、目的端口 1234（>1023），匹配 Rule B，被允许（Permit）。
- **Packet 3**（本地用户发送邮件到远程）：满足出站、源端口>1023、目的端口 25，匹配 Rule C，被允许（Permit）。
- **Packet 4**（远程 SMTP 服务器回复本地）：满足入站、源端口 25、目的端口 1357（>1023），匹配 Rule D，被允许（Permit）。
- **Packet 5**（外部尝试连接本地 8080 端口）：入站方向，但目的端口为 8080（非 25，不匹配 Rule A），源端口为 5150（非 25，不匹配 Rule D），最终落入默认策略 Rule E，被拒绝（Deny）。
- **Packet 6**（本地 8080 端口的响应包）：出站方向，但源端口为 8080（非 25，不匹配 Rule B），目的端口为 5150（非 25，不匹配 Rule C），最终落入默认策略 Rule E，被拒绝（Deny）。
