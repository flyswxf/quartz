Two-Phase Locking (2PL) 是一种​**​并发控制协议​**​，核心目标是确保多个事务并发执行时，结果等价于​**​某种串行执行​**​（即可序列化），通过严格管理事务对数据项加锁和解锁的时机来实现。

### 📌 核心思想

事务将其生命周期清晰地划分为两个不可逆的阶段：

1. ​**​增长阶段 (Growing Phase / Locking Phase / First Phase):​**​
    - 事务在此阶段可以​**​获取​**​锁（读锁、写锁等）, 将读锁升级为写锁。
    - 事务​**​不能释放​**​任何已经持有的锁。
    - 随着事务执行，它需要的锁集合只会​**​增长​**​（或保持不变）。
2. ​**​缩减阶段 (Shrinking Phase / Unlocking Phase / Second Phase):​**​
    - 事务在此阶段可以​**​释放​**​锁, 将写锁降级未读锁。
    - 事务​**​不能再获取​**​任何新的锁。
    - 锁的持有量​**​只减不增​**​。
    - 释放锁的顺序​**​通常无关紧要​**​。

当一个事务释放了它的第一个锁时，它就​**​正式从增长阶段进入了缩减阶段​**​。这是一个单向的过程。

---

### 🔒 锁的类型（关键）

2PL 的有效性依赖于​**​锁的粒度​**​（如行、表）和​**​锁的模式​**​：

1. ​**​共享锁 (Shared Lock / S Lock / Read Lock):​**​
    - 用于读操作。
    - 多个事务可​**​同时持有​**​同一数据项的共享锁。
    - 阻塞：任何试图获取该数据项​**​排他锁​**​的事务。
2. ​**​排他锁 (Exclusive Lock / X Lock / Write Lock):​**​
    - 用于写操作（插入、更新、删除）。
    - ​**​仅允许一个事务​**​持有某一数据项的排他锁。
    - 阻塞：任何试图获取该数据项​**​共享锁或排他锁​**​的事务。
![[assets/锁冲突矩阵.png]]
如果区分不同粒度的锁(对表加锁, 对记录加锁), 还有其他3种锁
3. Intention-Shared (IS):
	- 对节点加锁, 则事务​**​预先声明​**​它​**​可能对下层节点（子节点）​**​ 加​**​共享锁（S Lock）​**
4. Intention-Exclusive (IX):
	- 对节点加锁, 则事务​**​预先声明​**​它​**​可能对下层节点（子节点）​**​ 加​**​排他锁（X Lock）​**​。
	- #### 预期只对一些子节点加排他锁, 所以可以与IX, IS兼容, 但不能和对全部子节点加锁的锁兼容(比如S, X, SIX)
5. Shared+Intention-Exclusive (SIX):
	- 这是一个​**​组合锁​**​。事务​**​持有​**​父节点的 ​**​S 锁​**​，并且​**​同时持有​**​父节点的 ​**​IX 锁​**​。这表示事务：
		- ​**​当前以只读方式锁定了整个父对象（如整张表）​**​
		- ​**同时可能在表内某些子节点上进行修改（写操作）。**

### 💻 2PL 如何确保可串行化

1. ​**​冲突访问：​**​ 当两个事务想要​**​冲突地访问​**​同一个数据项（例如，一个写一个读，或两个写）时，2PL 规则确保它们不能同时持有冲突的锁。
2. ​**​锁阻塞：​**​ 如果一个事务请求的锁与另一个事务持有的锁冲突，请求的事务会被​**​阻塞​**​，直到另一个事务释放相应的锁。
3. ​**​两阶段保证：​**​ “增长阶段 + 锁不能提前释放” 保证了事务已经读取或修改的所有数据项的锁都被持有，直到该事务本身完成其关键读取和所有写入操作。这种“保守”的策略有效地​**​约束了事务之间可能的交错顺序​**​。
4. ​**​消除循环依赖：​**​ 最终，2PL 产生的冲突依赖关系图中​**​不会出现环​**​（如果严格遵守协议），从而保证了调度是[[可串行化#冲突可串行化Conflict Serializablity|冲突可串行化的]]（Conflict Serializable）。并行调度一定能转换为串行调度, 顺**序是各事务是按获得它最后一个锁的顺序**

### 🚫 2PL 的缺陷

1. ​**​死锁 (Deadlock):​**​
    - ​**​最主要的问题！​**​ 两个或多个事务彼此阻塞了对方所需资源。
    - 例如：T1 锁定了数据项 A，等待数据项 B；同时 T2 锁定了数据项 B，等待数据项 A。彼此无限等待。
    - ​**​解决方法：​**​ DBMS 需要实现​**​死锁检测​**​（通过等待图查找环）然后​**​终止/回滚其中一个事务​**​，或使用​**​锁超时​**​机制防止无限期阻塞。
2. ​**​级联回滚 (Cascading Rollbacks):​**​
    - 问题描述：事务 T1 修改了一个数据项 X 并​**​解锁（进入了缩减阶段）​**​。另一个事务 T2 读取了这个已被 T1 修改但未提交的 X。如果 T1 ​**​随后失败回滚​**​，那么 T2 已经读取了一个从未真实存在过的值（​**​脏读​**​），因此 T2 也必须回滚。如果 T2 修改了其他数据，可能导致更多事务回滚，形成“级联效应”。
    - ​**​根源：​**​ 在缩减阶段​**​提前释放了锁（特别是写锁）​**​。
    - ​**​严格2PL (Strict 2PL):​**​ 最常用变体！写锁（X Lock）只能在事务​**​提交​**​或​**​回滚​**​时释放。共享锁（S Lock）仍可提前释放。​**​严格2PL 完全避免了脏读和级联回滚​**​。
    - ​**​强2PL (Strong 2PL / Rigorous 2PL):​**​ 更严格变体！​**​所有锁​**​（读锁和写锁）都只能在事务​**​提交​**​或​**​回滚​**​时释放。保证了生成的可串行化顺序就是事务实际提交的严格顺序。并发度最低。**现实数据库通常使用强2PL**
3. ​**​锁开销：​**​ 获取、维护、检查和释放锁本身需要 CPU 和内存资源。
4. ​**​阻塞 (Blocking / Delay)：​**​ 等待锁会导致事务延迟，降低并发性能（吞吐量/响应时间）。尤其是在冲突较多的场景。

### 🌈 重要变体总结

| 变体                   | 读锁释放时机       | 写锁释放时机       | 优势          | 劣势          |     |
| -------------------- | ------------ | ------------ | ----------- | ----------- | --- |
| ​**​基本2PL​**​        | 缩减阶段         | 缩减阶段         | “理论”原型      | 级联回滚风险，无脏读？ |     |
| ​**​严格2PL (常用)​**​   | 缩减阶段         | ​**​事务结束​**​ | 避免脏读 & 级联回滚 | 仍有阻塞        |     |
| ​**​强2PL (严谨2PL)​**​ | ​**​事务结束​**​ | ​**​事务结束​**​ | 最严格保证，无脏读级联 | 并发度最低，最可能阻塞 |     |

### 📌 总结

- ​**​2PL 是什么？​**​ 一个保证冲突可串行化的事务调度协议，核心是加锁解锁分两阶段（先锁，后解锁）。
- ​**​关键规则：​**​ 增长阶段只能加锁不能放锁；缩减阶段只能放锁不能加锁。
- ​**​如何保证串行化？​**​ 通过锁机制约束冲突操作顺序，确保无环依赖图。
- ​**​主要问题：​**​ 死锁、潜在的级联回滚、阻塞。
- ​**​实用变体：​**​ ​**​严格2PL​**​（写锁事务结束时释放）是数据库中最常用的实现，有效避免了脏读和级联回滚。​**​强2PL​**​（所有锁事务结束时释放）保证最严格。

尽管 2PL（尤其是严格变体）被广泛实现和使用，但为了克服死锁和阻塞问题，许多现代数据库系统大量结合了 ​**​多版本并发控制 (MVCC)​**​ 技术来实现更高级别的隔离（如快照隔离），在读取和写入之间提供更好的并发性。
