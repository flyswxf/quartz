# 测试异味 (Test Smells)

Test Smells（测试异味）是指测试代码中那些**设计不当、难以维护、容易出错或难以理解**的编码模式。虽然它们可能不会导致编译错误或测试失败，但会增加维护成本，降低测试质量，甚至掩盖生产代码的问题。

## 1. 常见的测试异味分类

### 1.1 经典测试异味 (Literature Test Smells)
*来源: Deursen et al. 2001*

| 异味名称                            | 缩写 | 描述                                                           | 后果                                           |
| :---------------------------------- | :--- | :------------------------------------------------------------- | :--------------------------------------------- |
| **Assertion Roulette** (断言轮盘赌) | AR   | 一个测试方法包含多个没有解释信息（message）的断言。            | 测试失败时难以快速定位是哪个断言出错了。       |
| **Eager Test** (急切测试)           | EGT  | 一个测试用例检查了被测对象的太多功能（调用多个方法）。         | 测试逻辑复杂，难以维护；失败原因难以隔离。     |
| **General Fixture** (通用夹具)      | GF   | `setUp` 初始化了过于通用的环境，包含很多当前测试不需要的对象。 | 增加运行开销；阅读代码时困惑测试到底依赖什么。 |
| **Lazy Test** (懒惰测试)            | LT   | 多个测试用例都针对同一个被测方法（通常因为该方法太复杂）。     | 测试冗余，增加维护成本。                       |
| **Mystery Guest** (神秘嘉宾)        | MG   | 测试依赖外部资源（如文件、数据库），但在代码中看不出资源内容。 | 可读性差，必须打开外部文件才能理解测试数据。   |
| **Resource Optimism** (资源乐观)    | RO   | 乐观地假设外部资源（如路径、数据库）一定存在且状态正确。       | 导致测试不稳定（Flaky Tests）。                |
| **Sensitive Equality** (敏感相等)   | SE   | 在断言中依赖对象的 `toString()` 来判断相等。                   | `toString` 格式一变测试就挂，极其脆弱。        |

### 1.2 新近提出的测试异味 (Recently Proposed Test Smells)
*来源: Peruma et al. 2019*

| 异味名称                                        | 缩写 | 描述                                                                     |
| :---------------------------------------------- | :--- | :----------------------------------------------------------------------- |
| **Conditional Test Logic** (条件测试逻辑)       | CTL  | 测试代码包含 `if`, `switch`, `for` 等控制流。测试应该是一条直线。        |
| **Constructor Initialization** (构造函数初始化) | CI   | 在构造函数中初始化字段，而不是使用 `@Before`/`setUp`。可能导致状态污染。 |
| **Empty Test** (空测试)                         | ET   | 测试方法体内没有任何执行语句。                                           |
| **Exception Catch/Throw** (异常捕获/抛出)       | ECT  | 手动 `try-catch` 异常来判断测试结果，而不是利用框架特性。                |
| **Print Statement** (打印语句)                  | PS   | 包含 `System.out.println` 等冗余输出，拖慢测试且无助于自动化验证。       |
| **Redundant Assertion** (冗余断言)              | RA   | 断言永远为真或永远为假，毫无意义。                                       |
| **Sleepy Test** (嗜睡测试)                      | ST   | 使用 `Thread.sleep()` 强制等待。导致测试变慢且不稳定。                   |
| **Duplicate Assert** (重复断言)                 | DA   | 多次测试同一个条件。                                                     |
| **Unknown Test** (未知测试)                     | UT   | 没有断言语句的测试。                                                     |
| **Ignored Test** (忽略测试)                     | IT   | 使用 `@Ignore` 禁用的测试。                                              |
| **Magic Number Test** (魔法数字)                | MNT  | 使用了含义不明的数字字面量。                                             |

## 2. 典型案例分析

### 2.1 Conditional Test Logic (CTL) - 条件逻辑
**问题代码**：
```java
@Test
public void testSpinner() {
    for (Map.Entry<String, String> entry : map.entrySet()) { // 循环
        if (resultObject instanceof EventsModel) {           // 条件判断
            // ...
        }
    }
}
```
**分析**：测试代码应该简单明了（Setup -> Act -> Assert）。引入循环和条件判断意味着测试逻辑过于复杂，或者试图在一个测试里覆盖太多情况。这会导致某些分支可能根本没测到（False Confidence）。

### 2.2 Constructor Initialization (CI) - 构造函数初始化
**问题代码**：
```java
public class TagEncodingTest {
    public TagEncodingTest() {
        crypto = new CryptoComponentImpl(); // 在构造函数中初始化
    }
    @Test public void testA() { ... }
}
```
**分析**：JUnit 不保证为每个测试方法重新调用构造函数（取决于运行器配置）。这可能导致多个测试共享同一个实例，前一个测试修改的状态会污染后一个测试（State Pollution）。**正确做法**是使用 `@Before` 或 `@BeforeEach`。

### 2.3 Exception Catch/Throw (ECT) - 异常处理
**问题代码**：
```java
@Test
public void realCase() {
    try {
        a.compute();
    } catch (Exception e) {
        Assert.fail(e.getMessage()); // 手动捕获并失败
    }
}
```
**分析**：多此一举。如果抛出异常，测试框架会自动标记失败并打印堆栈。手动捕获反而可能掩盖真实的堆栈信息。**正确做法**是直接调用，或者使用 `assertThrows` (JUnit 5) / `@Test(expected=...)` (JUnit 4) 来测试预期异常。

### 2.4 Sleepy Test (ST) - 嗜睡测试
**问题代码**：
```java
assertEquals("Searching", entry.english);
Thread.sleep(500); // 强制休眠
final Intent i2 = getStartedActivityIntent();
```
**分析**：使用硬编码的时间等待异步操作。时间太短会导致测试偶尔失败（Flaky），时间太长会导致测试套件运行极其缓慢。**正确做法**是使用异步测试工具（如 Awaitility）进行轮询等待。

## 3. 研究发现

对 12 个系统的研究揭示了以下关于 Test Smells 的事实：
1.  **演变趋势**：随着时间推移，测试异味的总数在**增加**，但密度（每千行代码）保持相对稳定。
2.  **开发者态度**：开发者通常**缺乏动力**去主动修复测试异味。
3.  **与质量的关系**：**强相关**。特定的测试异味（如 CTL, ECT, MG）与生产代码的**缺陷倾向 (Defect-proneness)** 呈正相关。这意味着烂的测试代码往往暗示着烂的生产代码设计。

## 4. 消除 Test Smell 的基本方法

消除测试异味不仅仅是清理代码，更是为了提高测试的**可读性、稳定性和执行速度**。

### 4.1 遵循 AAA 模式 (Arrange-Act-Assert)
保持测试结构清晰：
*   **Arrange (准备)**: 设置测试数据和环境。
*   **Act (执行)**: 调用被测方法。
*   **Assert (断言)**: 验证结果。
*   *避免在测试中使用控制流（if/for/switch）。*

### 4.2 使用测试框架提供的特性
*   **生命周期管理**：使用 `@Before`/`@After` (JUnit 4) 或 `@BeforeEach`/`@AfterEach` (JUnit 5) 来管理夹具（Fixture），确保每个测试独立。
*   **异常测试**：使用 `assertThrows` 或 `ExpectedException` 规则，而不是手动 try-catch。

### 4.3 优化断言 (Improve Assertions)
*   **Assertion Roulette**: 为每个断言添加描述信息，或使用 AssertJ 等流式断言库，使错误信息更语义化。
    *   *Bad*: `assertTrue(list.size() == 5)`
    *   *Good*: `assertThat(list).hasSize(5)`
*   **Sensitive Equality**: 不要依赖 `toString()`，而是重写 `equals()` 或使用字段级比较（如 `assertThat(actual).usingRecursiveComparison().isEqualTo(expected)`）。

### 4.4 消除对外部资源的直接依赖 (Avoid Mystery Guest)
*   使用 **Mock/Stub** (测试替身) 来模拟数据库、文件系统或网络请求。
*   如果必须使用文件，尽量在测试代码中构造数据（如内存数据库、临时文件），或者在测试名和变量名中清楚地指明使用了哪个资源文件。

### 4.5 避免硬编码等待 (Avoid Sleepy Test)
*   **禁止**使用 `Thread.sleep()`。
*   **使用** `Awaitility` 等库进行条件轮询：
    ```java
    await().atMost(1, SECONDS).until(() -> myService.getStatus() == READY);
    ```

### 4.6 保持测试独立 (Isolation)
*   确保一个测试的执行不会影响另一个测试。
*   不要在测试类实例字段中保存状态（除非是 `@BeforeClass` 初始化的静态常量），尽量在 `@Before` 中重置。

### 4.7 拆分过大的测试 (Refactoring Eager Test)
*   如果一个测试方法测了太多东西，将其拆分为多个专注于单一行为的小测试。
*   提取公共的初始化代码到 `@Before` 或辅助方法（Helper Method）中。
