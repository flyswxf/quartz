**测试替身 (Test Double)** 泛指在测试过程中用来替代真实代码（如类、模块、函数、API 等）的代码。

在测试术语中，通常涉及两个角色：
*   **CUT (Code Under Test)**：被测代码（或 SUT - System Under Test）。
*   **DOC (Depended-on Component)**：被测代码所依赖的组件。

测试替身的作用就是替换掉真实的 **DOC**，让 **CUT** 在一个受控的环境中运行。

## 为什么需要测试替身？

1.  **隔离被测代码**：解除 **CUT** 与 **DOC** 的强耦合，确保测试失败是因为被测代码的问题，而不是依赖项的问题。
2.  **加速测试执行**：真实的依赖项（如数据库、网络请求）通常很慢，替身可以瞬间返回结果。
3.  **模拟难现场景**：真实依赖可能很难产生特定的错误（如网络超时、磁盘已满），替身可以轻松模拟。
4.  **消除不确定性**：真实依赖可能返回不确定结果（如 `Date.now()`、`Math.random()`），替身提供确定性返回值。

## 什么时候使用？

根据经验，并非所有依赖都需要模拟。

### ✅ 建议模拟 (Mock or Stub)
*   **太慢的依赖**：如数据库操作、复杂算法。
*   **外部基础设施**：如 HTTP API、消息队列、发送邮件。
*   **难以控制的场景**：如模拟 2月29日、模拟网络断开。

### ❌ 不建议模拟 (Do not Mock)
*   **实体 (Entities)**：简单的数据持有对象。
*   **原生库与工具方法**：如 `List`, `Map`, `Math.max()`。
*   **足够简单的逻辑**：直接使用真实对象成本更低且更可靠。

## 测试替身的类型

测试替身主要分为五种类型（Dummy, Stub, Spy, Mock, Fake）：

### 1. Dummy Object (哑元)
*   **定义**：仅用于填充参数列表，**从未被真正使用**。
*   **场景**：API 要求必须传一个参数，但测试逻辑完全不关心这个参数。
*   **例子**：
    ```java
    // 只需要 list 既可，不需要 list 里有什么
    bookService.count(new ArrayList<>()); 
    ```

### 2. Test Stub (桩)
*   **定义**：提供**预设的返回值**（Canned Answer），不包含验证逻辑。
*   **场景**：被测系统需要从外部获取数据才能继续运行。
*   **例子**：
    ```java
    // 无论谁调用，都返回 true
    when(authService.checkPermission(any())).thenReturn(true);
    ```

### 3. Test Spy (间谍)
*   **定义**：像 Stub 一样工作，但会**记录调用细节**（调用次数、参数）。
*   **场景**：需要断言某个副作用（Side Effect）是否发生，但无法通过返回值验证。
*   **例子**：
    ```java
    // 记录 logger 是否被调用了
    verify(logger).info("User logged in");
    ```

### 4. Mock Object (模拟)
*   **定义**：预先编程了**期望 (Expectation)** 的对象。如果交互不符合预期（如方法未被调用、参数错误），测试会自动失败。
*   **场景**：**行为验证**，关注对象之间的交互方式。
*   **例子**：
    ```java
    // 期望 emailService.send 被调用一次，且参数必须是 user
    mockEmailService.expect(once()).method("send").with(user);
    ```

### 5. Fake Object (伪造)
*   **定义**：拥有**可工作的实现**，但采用了简化方式（通常不适合生产环境）。
*   **场景**：替代重量级的依赖，进行集成测试。
*   **例子**：
    *   使用 **H2 内存数据库** 替代 MySQL。
    *   使用 `HashMap` 在内存中模拟文件系统。

## ⚠️ 缺点与风险

虽然测试替身很有用，但也有代价：

1.  **Mock Drift (模拟漂移)**：
    *   风险：如果真实组件 (DOC) 的代码修改了，但 Mock 没有同步更新。
    *   后果：**测试依然通过，但生产环境会崩溃**。
2.  **测试代码耦合度增加**：
    *   风险：使用 Mock 的测试通常需要了解被测对象的**内部实现细节**（例如：它调用了 A 方法还是 B 方法？）。
    *   后果：重构生产代码时，即使功能没变，测试也容易报错（脆弱的测试）。

## 💡 最佳实践

*   **依赖注入 (Dependency Injection)**：为了方便替换替身，被测类应通过**构造函数**接收依赖，而不是在内部 `new` 对象。
*   **只模拟必要的 (Only mock what is necessary)**：不要为了模拟而模拟，过多的 Mock 会让测试变得难以维护。
