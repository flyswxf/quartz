## 1. 什么是可测性？

**可测性 (Testability)** 是指为了测试目的，去**控制 (Control)** 和**观察 (Observe)** 系统或组件行为的难易程度。

*   **核心要素**:
    *   **可控性 (Controllability)**: 能否方便地让系统进入特定状态？（例如：模拟数据库连接失败、模拟特定的时间点）。
    *   **可观测性 (Observability)**: 系统运行后，能否方便地验证结果？（例如：直接获取返回值、查询状态，而不是去查日志或数据库）。
*   **价值**: 高可测性的系统允许以最小的代价编写高效、稳定的测试。

## 2. 核心原则

### 2.1 关注点分离 (Separation of Concerns)
*   **原则**: 将 **业务逻辑 (Domain Code)** 与 **基础设施代码 (Infrastructure Code)** 分开。
    *   **业务逻辑**: 核心规则、实体、算法。应该能独立测试，运行速度快。
    *   **基础设施**: 数据库、文件 I/O、网络请求。通常难以测试且运行缓慢。
*   **目的**: 隔离变化，让我们能专注于测试高价值的业务逻辑，而无需启动笨重的外部环境。

### 2.2 可控性 (Controllability) 与 依赖注入
*   **问题**: 在代码内部直接 `new` 具体实现类（如 `new ShoppingCartHibernateDao()`）会导致硬编码依赖，无法在测试中替换。
*   **解决方案**: **依赖注入 (Dependency Injection, DI)**。
    *   **构造函数注入**: 通过构造函数将依赖传递给对象，而不是由对象自己创建。(就是传递参数而非new参数)
    *   **测试时的优势**: 可以传入 **Mock (模拟对象)** 或 **Stub (桩)** 来完全控制被测对象的外部环境（例如让 Mock 数据库直接返回预设数据）。

### 2.3 可观测性 (Observability)
*   **挑战**: 如何验证没有返回值 (`void`) 的方法或私有状态的变化？
*   **解决方案**:
    1.  **行为验证 (Behavior Verification)**: 使用 Spy/Mock 验证某个方法是否被调用（例如 `verify(db).persist(cart)`）。
    2.  **状态验证 (State Verification)** (推荐): 暴露适当的读取方法 (Getter) 或让方法返回计算结果，直接断言最终状态（例如 `assertTrue(cart.isReady())`）。
    3.  **显性化隐性结果**: 如果一个 `void` 方法计算了复杂数据并存库，考虑将其改为返回这些数据，以便直接测试计算逻辑。

## 3. 案例分析：购物车 (Shopping Cart Demo)

### 3.1 糟糕的设计 (不可测)
```java
public void processAll() {
    // 硬编码依赖，无法替换，必须连真实数据库
    ShoppingCartHibernateDao db = new ShoppingCartHibernateDao();
    // ...
}
```

### 3.2 好的设计 (高可测)
使用**构造函数注入**：
```java
public class PaidShoppingCartsBatch {
    private ShoppingCartRepository db;

    public PaidShoppingCartsBatch(ShoppingCartRepository db, ...) {
        this.db = db;
    }
    
    public void processAll() {
        // 使用注入的 db，测试时可以是 Mock 对象
        List<ShoppingCart> carts = db.cartsPaidToday(); 
        // ...
    }
}
```

### 3.3 测试示例
利用 Mock 对象控制环境，利用 Spy 或断言验证结果：
```java
@Test
public void happyPath() {
    // 1. Setup: 注入 Mock 依赖
    PaidShoppingCartsBatch batch = new PaidShoppingCartsBatch(mockDb, mockService, ...);
    
    // 2. Stub: 控制 Mock 行为 (让数据库返回假数据)
    when(mockDb.cartsPaidToday()).thenReturn(Arrays.asList(testCart));
    
    // 3. Execute
    batch.processAll();
    
    // 4. Verify: 验证结果 (状态验证优先)
    assertThat(testCart.isReadyForDelivery()).isTrue();
}
```

## 4. 实战建议

*   **高内聚 (Cohesion)**: 确保每个类单一职责。
*   **低耦合 (Coupling)**: 减少类之间的依赖，降低 Mock 成本。
*   **私有方法**: **不要直接测试私有方法**。通过测试公开接口 (Public API) 来覆盖私有逻辑。
*   **静态方法**: 慎用静态方法，它们很难 Mock，会破坏可测性。

## 5. 总结
**"Designing for testability is not just about writing tests; it’s about designing systems that are inherently testable."**
为可测性而设计，不仅仅是为了写测试用例，更是为了构建低耦合、高质量、易维护的系统。
