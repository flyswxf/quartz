# Hypothesis Shrinker 模块优缺点与技术落地反思

## 一、核心模块优缺点分析

### 1.1 设计优点

**模块化的 Pass 架构 （高可扩展性）**

Shrinker 将收缩策略抽象为独立的 ShrinkPass 对象，每个 pass 封装特定的启发式算法。从 `shrinker.py:310-324` 可见 13 个 pass 依次注册，新增策略只需实现符合 `chooser` 接口的函数即可插入。这种设计使得：

- 添加新的类型专用优化（如针对树结构、图结构）无需修改框架
- Pass 之间完全解耦，可独立测试和调优
- 通过统计信息（calls、shrinks、deletions）精确评估每个 pass 的效果

**效率**

采用 shortlex（先比较长度，再比较字典序（比较长度更节省性能））作为全局目标函数，而且有像`find_integer` 函数这些利用了指数增长+二分搜索的探索方式，避免了穷举搜索。通过 `consider_new_nodes` 立即验证并更新 `shrink_target`，使得后续 pass 总是在当前最优解上工作，形成单调递减的收缩链。

**可重现性**

通过 `chooser` 抽象和强制 `sorted()` 调用，确保相同输入产生相同收缩路径。配合 `derived_value` 装饰器的缓存失效机制，在 shrink_target 更新时自动清除陈旧派生值，避免状态不一致。

这使得测试失败可精确复现，特别是对于在一些频繁的 CI 环境中的调试分析。

**局部性假设**

所有多节点协同 pass 一般会限制搜索窗口为 3-4 个节点，基于**相关数据通常相邻生成**的启发式。这将尽可能的避免了 O(n²) 的复杂性，同时保持大部分情况的有效性 。

### 1.2 设计局限性

**性能开销：测试函数重复执行次数较多**

每次 `consider_new_nodes` 都需要完整执行一次测试函数。在对`lower-int-together`的pass的调试中共计 91 次调用意味着测试代码被执行了 91 次。对于慢速测试（如涉及网络请求、数据库操作），收缩可能耗时数分钟。

**Pass 执行顺序**

固定的 pass 列表执行顺序（`shrinker.py:310-324`）可能导致次优解。例如在我们调试 `lower-int-together`时如果 `lower_integers_together` 排在 `minimize_individual_choices` 之前，可能会更早发现 `(5, 25)`的最优情况。但是当前设计依赖"循环执行直到无进展"来弥补顺序问题，很容易存在一些冗余调用。

## 二、技术落地反思

### 2.1 对同类工具的借鉴意义

Pass 之间的松耦合使得算法迭代成本极低（就像`redistribute_numeric_pairs`、`lower_integers_together`等pass），这对需要频繁实验的验证工具比较有用：

- 可快速添加特定情况下的专用 pass 进行优化
- 可通过 A/B 测试评估新 pass 的实际效果

### 2.2 工程实现的可优化方向

在调试过程中，我们发现当前收缩是严格串行的（每次只尝试一个修改）。对于某些特定场景下的慢速测试，可并行化提升效率：

比如：

```python
# 为每个 pass 维护独立的候选队列
candidates = {
    pass1: [...],
    pass2: [...]
}

# 并行执行不冲突的修改
with ThreadPoolExecutor() as executor:
    futures = [executor.submit(test, c) for c in next_batch()]
    results = [f.result() for f in futures]
```

不过关键还是在于如何判断两个修改之间是不冲突的，以及如何合并并行发现的多个改进？
